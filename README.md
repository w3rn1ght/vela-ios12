# Vela — VPN-клиент для джейлбрейкнутого iOS 12

Клиент в духе Shadowrocket: список серверов, выбор активной ноды, пинг, подписки.
Под капотом — ядро [sing-box](https://github.com/SagerNet/sing-box), которое демон
запускает от root и заворачивает в `utun` без `NetworkExtension`.

```
[Vela.app]  --unix socket-->  [velad]  --fork-->  [sing-box]
                                 |                   |
                                 |                   +--> utunN --> трафик
                                 +--> route add 0.0.0.0/1, 128.0.0.0/1 --> utunN
```

- Репозиторий: https://github.com/w3rn1ght/vela-ios12
- **Готовая сборка:** https://github.com/w3rn1ght/vela-ios12/releases/latest
  (`com.vela.vpn_0.2.0_iphoneos-arm.deb`, собрана GitHub Actions; все бинари
  arm64 / platform ios / minos 12.0)

> Код собрался и прошёл тесты парсера в CI, но на реальном устройстве пока не
> обкатан: создание `utun`, установка маршрутов и перехват DNS — это то, что
> проверяется установкой.

## Что нового в 0.2.0

- **Список серверов**: ноды из ссылок и подписок сохраняются в
  `/var/mobile/Library/Vela/nodes.json` (0600), переживают перезапуск.
- **Выбор сервера**: тап по строке — нода активна (галочка). Подключение идёт
  ровно к выбранной ноде.
- **Пинг**: тянем вниз список или жмём «Пинг» — TCP-замер до `server:port`
  выполняется в демоне с привязкой к физическому интерфейсу (`IP_BOUND_IF`),
  поэтому цифры честные и при поднятом туннеле.
- **Новый интерфейс**: таблица вместо текстового поля, поле ввода ссылок
  больше не «уезжает» под навигационную панель (Auto Layout + safe area,
  `textContainerInset`).
- **Иконка** и имя **Vela** (пакет `com.vela.vpn`, демон `velad`), старый
  `com.happvpn.jb` при установке удаляется автоматически.
- **Подписки**: заголовки `x-hwid` / `x-device-os` / `x-ver-os` /
  `x-device-model`, User-Agent v2rayNG, импорт Xray-JSON, отчёт о загрузке
  в экране «Лог».

## Поддерживаемые ссылки

| Схема | Протокол | Примечания |
|---|---|---|
| `vless://` | VLESS | TLS, Reality, WS, gRPC, HTTP/2, HTTPUpgrade, `flow=xtls-rprx-vision` |
| `vmess://` | VMess | base64-JSON (v2rayN), WS/gRPC/HTTP2/TCP, TLS |
| `trojan://` | Trojan | TLS, WS/gRPC |
| `ss://` | Shadowsocks | оба формата ссылок, плагины `obfs-local` / `v2ray-plugin` |
| `hysteria2://`, `hy2://` | Hysteria2 | TLS, `obfs=salamander` |
| `tuic://` | TUIC v5 | `uuid:password` |
| `https://…` | подписка | base64, plain-список, Xray-JSON |

**Не поддерживается:**

* `happ://crypt…` — зашифрованная подписка Happ; ключ внутри их приложения.
  Берите обычную ссылку на ноду или https-подписку (см. ниже).
* TUIC v4 (`token=`), VMess TCP+HTTP-обфускация, mKCP.
* Транспорт `xhttp` — ядро sing-box 1.8 его не умеет; такие ноды в списке
  помечены «не поддерживается» и не выбираются.

## Подписки с HWID (Remnawave и совместимые)

Панели привязывают подписку к устройству заголовком `x-hwid`. Без него вместо
нод приходят 4 заглушки `vless://000…@0.0.0.0:1` с текстом «Включите передачу
HWID». Vela генерирует UUID один раз, хранит его в `NSUserDefaults` и отправляет
вместе с остальными заголовками.

Проверено на реальной подписке такого типа: без HWID — 4 заглушки, с HWID —
157 нод (148 `vless` + 9 `ss`); 139 из них разбираются ядром, 18 используют
`xhttp`. Если нод не осталось, приложение покажет отчёт: HTTP-код, размер,
формат ответа и первые строки.

### Лимит устройств (главная причина «подписка не работает»)

Панель пускает только N устройств, и «устройство» — это HWID. Проверено на
живой подписке: первый HWID получил 157 нод, а любой следующий — 996 байт
заглушек `0.0.0.0:1`. То есть если слоты заняты, телефон будет получать
заглушки, сколько бы раз вы ни обновляли подписку.

Что делать:

1. **⚙ Настройки** в приложении показывает текущий HWID. Его можно
   скопировать и прислать провайдеру либо вписать в кабинет.
2. Там же — «Обновить подписку» (перезапрос без повторного вставления ссылки)
   и «Сгенерировать новый HWID».
3. Если у вас есть HWID уже разрешённого устройства (например, старого
   клиента) — вставьте его в поле и нажмите «Применить», затем «Обновить
   подписку».
4. Либо удалите лишние устройства в кабинете провайдера.

Отчёт о загрузке всегда лежит в `/var/mobile/Library/Vela/last-subscription.txt`
(в нём же текущий HWID) — удобно прислать по SSH, если экран не видно:

## Если у вас ссылка `happ://crypt…`

Это не адрес сервера, а зашифрованный контейнер (nonce + ciphertext + тег
AES-GCM), внутри — URL подписки и заголовки. Ключ лежит в приложении Happ,
снаружи его не достать, поэтому Vela такие ссылки отклоняет с объяснением.

Как получить рабочую ссылку:

1. Happ → список серверов → «Поделиться»/«Копировать ссылку» — получится
   обычная `vless://…`.
2. Взять у провайдера обычную `https://…/sub/…`.
3. Попросить у провайдера plain-ссылку.

## Требования и сборка

* iPhone/iPad **arm64**, iOS **12.x**, джейлбрейк с рабочим `launchd`.
* Для сборки: macOS + Xcode CLT + Go 1.21+ + Theos + `ldid`
  (или GitHub Actions — workflow в репозитории).

```bash
brew install go ldid
./scripts/build-core.sh          # sing-box 1.8.14, ios/arm64, min iOS 12.0
./scripts/run-parser-tests.sh    # офлайн-тесты парсера (без устройства)
export THEOS=~/theos
make package                     # -> packages/com.vela.vpn_0.2.0_*.deb
```

Иконка пересобирается скриптом `scripts/make_icon.py` (чистый Python, без PIL).

## Установка

```bash
scp com.vela.vpn_0.2.0_iphoneos-arm.deb root@IPHONE:/var/root/
ssh root@IPHONE
dpkg -i /var/root/com.vela.vpn_0.2.0_iphoneos-arm.deb
```

`postinst` создаёт каталоги, выставляет права, удаляет старый `HappVPN`,
загружает `com.vela.daemon` и делает `uicache` для `/Applications/Vela.app`.

Проверка:

```bash
launchctl list | grep vela
ls -l /var/mobile/Library/Vela/          # nodes.json, control.sock, core.json, core.log
```

## Использование

1. **＋** → вставить ссылку или https-подписку → «Добавить».
2. Тап по ноде — выбрать активную (галочка).
3. Потянуть список вниз — пинг всех нод (параллельно, 6 за раз).
4. «Подключить» внизу → статус в шапке: нода, протокол, `utun`.
5. «Лог» слева сверху — отчёт о подписке + лог ядра.

Список нод и выбранная нода сохраняются автоматически.

## Диагностика

| Что | Где |
|---|---|
| Лог демона | `/var/mobile/Library/Logs/Vela/daemon.log` |
| Лог ядра | `/var/mobile/Library/Vela/core.log` |
| Конфиг ядра | `/var/mobile/Library/Vela/core.json` |
| Ноды | `/var/mobile/Library/Vela/nodes.json` |
| Отчёт о подписке | `/var/mobile/Library/Vela/last-subscription.txt` (там же HWID) |
| Маршруты | `netstat -rn | head -20` (0/1 и 128/1 на utunN) |
| Подпись | `ldid -e /usr/libexec/vela/sing-box` |

Типичные проблемы:

* **«Демон не отвечает»** — `launchctl list | grep vela`; сокет должен быть
  `srw-rw-rw-`; приложение подписано `entitlements/app.plist`.
* **«Ядро не создало tun»** — entitlement `utun` у ядра; проверьте
  `/usr/libexec/vela/sing-box run -c /var/mobile/Library/Vela/core.json` вручную.
* **«Не удалось поставить маршруты»** — нет entitlement `net.route` или не root.
* **Подписка даёт заглушки** — см. раздел про HWID; отчёт в «Логе» покажет
  HTTP-код и формат ответа.
* **Нет интернета после падения** — `route delete -net 0.0.0.0/1` и
  `route delete -net 128.0.0.0/1` (демон делает это сам при старте и по SIGTERM).

## Ограничения

* Одна активная нода; переключение применяется при переподключении.
* Нет kill switch и авто-переустановки маршрутов при смене Wi-Fi ↔ LTE.
* Пинг — TCP-хендшейк (не полный URL-test через прокси); для Reality/TLS
  реальная задержка чуть выше.
* `xhttp` не поддерживается ядром 1.8 (нужен переход на 1.11+ и миграция конфига).
* Только IPv4 для host-маршрута до сервера; IPv6-сервер туннелируется частично.

## Права и безопасность

Инструмент — для подключения к **своему** серверу. Подписка и ключи лежат в
`/var/mobile/Library/Vela` (nodes.json — 0600); ссылка-подписка является
bearer-токеном, не публикуйте её.
